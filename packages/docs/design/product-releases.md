# 产品组合发布

Core、CLI、Web App、Desktop 和 Mobile 使用同一个产品版本和 `v<version>` Tag，在一个 GitHub Release 交付。`www-v<version>` 继续独立发布官网与文档。

产品版本以 CLI 的 Cargo 版本为准，Core、Web App、Desktop 和 Mobile 的发行版本必须与之相等。首个正式版前保持 `0.0.1` 基准及数据 epoch 1。各应用仍是独立构建目标，不再分别公开发布组件依赖。

## 构建顺序

身份检查后，Web App、macOS、Windows、Linux x64、Linux ARM64 原生程序、Android 和 iOS 并行构建。原生任务一次构建本平台的 CLI 和 Core；macOS 保留签名与公证。桌面 App 只等待本平台完整运行包，再与手机 App 一起进入完整产品汇总。

每个平台的完整安装包只等待该平台原生程序和 Web 制品，不等待其他平台。组包校验本次运行内的不可变制品 ID、源码、版本、目标平台和字节摘要，不从其他公开 Release 拉组件。

唯一创建任务先建立标明构建中的公开 Release。各组完成本地校验后，只追加自己独占名称的附件，用户可立即手动下载。`collect` 与平台上传并行，继续审计原始完整制品；最终任务在全套已公开附件与审计结果一致后，最后追加全局 `release.json`。缺失、损坏、错源或失败目标会阻止整套完成标记和自动消费，不把部分完成当作整套成功。

## 失败与恢复

构建、组包和公开发布分别记录状态。发布失败时复用原运行的完整制品，不为同一个 Tag 重建替换字节；网络响应未知时先查询远端事实。同一个构建中 Release 可继续追加其他平台的已校验附件；已有附件字节和历史 Tag 保持不可变。新版自动安装、更新与后续发布动作以最终清单为完成标记，旧客户端的既有行为无法被追溯修改。

每个 UTC 小时最多为产品组分配一个 Hourly 版本和 Tag，官网不参与 Hourly。npm 在完整产品公开后按渠道规则发布，不能代替产品构建验收。分发结果分别核对。

手动构建默认不公开发布，用于验证并行关系和最终交付物。真正发布必须指向已经进入 main、验证成功的固定提交及现存精确 Tag。
